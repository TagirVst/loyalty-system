# Staff / Barista Bot UX V2

## 1. Цель

Staff-бот — максимально быстрый рабочий интерфейс бариста на общем телефоне кафе. Он не содержит бизнес-логику loyalty: бот собирает ввод, backend проверяет права и рассчитывает результат.

Основные требования:
- одна продажа должна проводиться за минимальное число действий;
- свободный текст используется только там, где ввод числа действительно быстрее кнопок;
- все критические операции имеют preview/confirmation;
- интерфейс не раскрывает бариста лишние данные клиента;
- повторное нажатие кнопок не должно создавать дубли;
- один Telegram-профиль может быть staff terminal, но каждая операция принадлежит конкретному Staff и StaffSession.

## 2. Авторизация терминала

Администратор заранее разрешает Telegram-профиль/чат как StaffTerminal и связывает его с Location.

Если Telegram-профиль не разрешён:

```text
Этот Telegram-профиль не подключён как рабочий терминал.
Обратитесь к администратору.
```

Никакие staff-функции недоступны.

## 3. Вход бариста

Если терминал разрешён, но активной staff-session нет:

```text
Введите ваш 6-значный PIN
```

PIN:
- ровно 6 цифр;
- назначается администратором;
- уникален в пределах всей организации;
- принадлежит конкретному Staff;
- хранится только как hash;
- сотрудник должен быть active;
- сотрудник закреплён за Location этого терминала;
- после успешной проверки backend создаёт StaffSession;
- PIN никогда не используется как API token или staff_id.

Ошибки PIN не должны раскрывать, существует ли конкретный PIN/сотрудник.

Защита от перебора:
- после 5 неверных попыток — блокировка на 5 минут;
- при повторных сериях блокировка может прогрессивно увеличиваться;
- неудачные попытки входят в audit/security log.

После входа:

```text
Смена открыта
Бариста: Магомед
Точка: Тейкитерия

[ Новая продажа ]
[ Последняя операция ]
[ Мои операции ]
[ Выйти ]
```

Сессия действует до ручного выхода или административного завершения. Архитектура допускает будущую интеграцию с полноценными сменами/расписанием.

## 4. Быстрая смена сотрудника

Поскольку телефон общий, выход должен быть доступен с главного экрана одним действием.

После `Выйти`:

```text
Завершить работу Магомеда на этом терминале?

[ Да, выйти ] [ Назад ]
```

После подтверждения StaffSession закрывается и появляется ввод PIN следующего сотрудника.

## 5. Новая продажа

Кнопка `Новая продажа` создаёт OrderDraft на backend.

Шаг 1:

```text
Введите 5-значный код клиента

[ Отмена ]
```

Customer identification code:
- 5 цифр;
- TTL 90 секунд;
- одноразовый;
- связан с IdentificationSession;
- проверка кода не расходует его;
- код окончательно помечается использованным только внутри успешной транзакции подтверждения заказа.

Возможные ответы backend:
- код действителен;
- код неверен;
- код истёк;
- код уже использован;
- клиент заблокирован.

## 6. Карточка клиента для продажи

После успешного кода показывается только необходимое:

```text
Клиент найден
Уровень: Gold
Баллы: 1 240
Можно списать: будет рассчитано после суммы
Подарки: 2

[ Продолжить ]
[ Отмена ]
```

Не показывать бариста без необходимости:
- телефон;
- дату рождения;
- историю профиля;
- отзывы;
- административные заметки;
- полную историю покупок;
- другие PII.

## 7. Ввод заказа

Пока нет POS-интеграции, бариста вводит вручную:
- полную сумму заказа;
- количество поддерживаемых категорий.

Сначала сумма:

```text
Введите сумму заказа, ₽
```

Backend валидирует диапазон и формат. Ноль/отрицательные/аномальные значения отклоняются.

Затем категорийные счётчики:

```text
Напитки: 2
[ − ] [ + ]

Сэндвичи: 1
[ − ] [ + ]

[ Рассчитать ]
[ Назад ] [ Отмена ]
```

Категории полностью настраиваются из админки уже в первой версии. Бот получает активные категории из backend-конфигурации и не содержит жёстко прошитых `drinks`/`sandwiches`.

## 8. Order Preview

`Рассчитать` вызывает backend quote/preview. Backend определяет:
- уровень;
- qualification amount;
- cashback policy;
- применимые кампании;
- доступные rewards;
- стандартный или индивидуальный redemption limit;
- доступный баланс;
- максимальное списание;
- итоговое потенциальное начисление.

Пример:

```text
Заказ: 1 000 ₽
Уровень: Gold — 7%
Акция: x2 cashback

Доступно баллов: 1 240
Можно списать: до 300 ₽
Подарков доступно: 2

[ Списать баллы ]
[ Выбрать подарок ]
[ Без списания и подарков ]
[ Назад ] [ Отмена ]
```

Preview имеет ограниченный срок жизни/version. При подтверждении backend обязан пересчитать/проверить актуальность условий.

## 9. Правила базы для cashback и списания

### Cashback

Если баллы не используются, cashback рассчитывается от суммы, реально оплачиваемой деньгами после применённых скидок/наград.

Если использован хотя бы 1 балл, cashback за заказ = 0.

Пример:
- исходный заказ 1 000 ₽;
- скидка/награда уменьшила оплату до 800 ₽;
- points не использованы;
- cashback считается от 800 ₽.

### Лимит списания

Стандартный лимит списания points = 30% от суммы заказа после применения скидок/наград, но до списания самих points.

Для клиента может действовать временный индивидуальный override до 100%.

Backend всегда рассчитывает лимит сам.

## 10. Списание баллов

После `Списать баллы`:

```text
Можно списать до 300 баллов
Баланс: 1 240

Введите количество:

[ Максимум 300 ]
[ Назад ]
```

Backend проверяет сумму, баланс, актуальный redemption limit и состояние quote.

## 11. Округление баллов

Баллы хранятся и показываются как целые единицы.

Для начисления используется предсказуемое округление вниз:

```text
63.70 -> 63 points
63.99 -> 63 points
```

Нельзя использовать float для финансовых расчётов. Денежные суммы и проценты считаются через Decimal/integer minor units с явным rounding mode.

## 12. Подарки

`Выбрать подарок` показывает только реально доступные CustomerReward:

```text
Доступные подарки

Бесплатный напиток ×2
[ Использовать ]

Десерт ×1
[ Использовать ]

[ Готово ]
[ Назад ]
```

Можно выбрать несколько наград, если у клиента достаточно количества и правила наград допускают совместное применение.

Подарок и баллы могут использоваться в одном заказе.

Бариста не может:
- создать награду;
- изменить её срок;
- изменить количество;
- применить отсутствующую награду;
- обойти compatibility rules.

## 13. Финальное подтверждение

Перед финансово значимым действием обязательный финальный preview:

```text
Проверьте заказ

Сумма: 1 000 ₽
Баллы: −200
Подарок: Бесплатный напиток ×1
К оплате: 800 ₽
Начисление: 0 баллов
Причина: использованы баллы

[ Подтвердить продажу ]
[ Изменить ]
[ Отмена ]
```

Если баллы не используются:

```text
Сумма: 1 000 ₽
Акция: x2 cashback
Начисление: +140 баллов

[ Подтвердить продажу ]
```

`Подтвердить продажу` вызывает один идемпотентный backend command. В одной DB transaction фиксируются Order, IdentificationSession consumption, ledger, qualification, rewards, campaigns, tier changes, audit и domain events.

## 14. Успешная продажа

После commit:

```text
Продажа проведена
1 000 ₽

Баллы: −200
Подарок: напиток ×1

[ Новая продажа ]
[ Операция ]
```

Клиентский бот получает отдельное уведомление о покупке/баллах/уровне/подарках через notification module.

## 15. Последняя операция

Главный экран содержит `Последняя операция`.

Бариста видит только собственную последнюю операцию текущей staff-session или разрешённого рабочего периода.

```text
Заказ #A1042
1 000 ₽
14:32

Баллы: −200

[ Отменить ошибочную операцию ]
[ Назад ]
```

Кнопка отмены доступна только пока backend сообщает `can_cancel=true`.

## 16. Отмена и возвраты

### Быстрая отмена баристой

Бариста может полностью отменить только свою ошибочную операцию в течение 10 минут.

Backend повторно проверяет:
- заказ принадлежит текущему Staff;
- операция допускает barista cancellation;
- прошло не более 10 минут;
- заказ ещё не отменён/возвращён;
- StaffSession/permission действительны.

После 10 минут требуется администратор.

### Частичные возвраты

Архитектура сразу поддерживает partial refund, даже если UX первой версии использует его в основном из админки/POS-интеграции.

Возврат моделируется отдельной сущностью/операцией, связанной с исходным Order, с указанием возвращаемой суммы/позиций/категорий и собственного idempotency key.

Backend по правилам конкретных reward/campaign:
- возвращает ранее списанные points в соответствующей части;
- создаёт compensating ledger entries для ранее начисленных points;
- уменьшает qualification amount;
- пересчитывает automatic tier при необходимости;
- восстанавливает reward entitlement полностью или частично, если это допустимо;
- пишет audit/domain events.

Исходный заказ и исходные ledger entries не изменяются и не удаляются.

## 17. Мои операции

Нужен короткий рабочий список, а не полноценная аналитика:

```text
Сегодня

14:32 — 1 000 ₽ — проведено
14:18 — 650 ₽ — проведено
13:51 — 420 ₽ — отменено
```

Доступны только операции самого сотрудника. Полная история сети — админка.

## 18. Клиент заблокирован

Если клиент заблокирован:

```text
Программа лояльности для этого клиента недоступна.
Продолжить операцию через loyalty нельзя.

[ Закрыть ]
```

Бариста не видит причину блокировки, если backend явно не разрешает её показывать.

## 19. Ошибки и восстановление сценария

Нельзя показывать stack traces/HTTP status как основной текст.

Типовые машинные ошибки backend мапятся на понятные сообщения:
- `IDENTIFICATION_EXPIRED` → «Код клиента истёк. Попросите новый код.»
- `INSUFFICIENT_POINTS` → «Баланс изменился. Пересчитайте заказ.»
- `REWARD_UNAVAILABLE` → «Подарок уже недоступен. Пересчитайте заказ.»
- `QUOTE_STALE` → «Условия заказа изменились. Выполнен новый расчёт.»
- `STAFF_SESSION_ENDED` → «Сессия сотрудника завершена. Войдите снова.»
- `ORDER_ALREADY_CONFIRMED` → показать уже созданный результат вместо повторной продажи.

При временной сетевой ошибке подтверждение нельзя автоматически считать неуспешным: бот запрашивает статус idempotency key и показывает фактический результат.

## 20. Управление сообщениями

Рабочий чат не должен превращаться в журнал из десятков меню.

Предпочтение:
- inline keyboards;
- редактирование текущего рабочего сообщения при переходах;
- отдельные новые сообщения только для важных итогов/событий;
- кнопки `Назад` и `Отмена` в многошаговых сценариях;
- callback содержит только короткий action/token, а не доверенные бизнес-данные.

## 21. Защита от человеческих ошибок

- Нельзя подтвердить заказ без финального preview.
- Нельзя дважды подтвердить один draft.
- Нельзя использовать один customer code в двух подтверждённых заказах.
- Нельзя списать больше рассчитанного backend лимита.
- Нельзя уйти в отрицательный points balance.
- Нельзя дважды погасить один reward quantity.
- При устаревшем preview backend требует пересчёт.
- Отмена черновика ничего финансового не меняет.

## 22. POS-интеграция в будущем

Staff-бот не должен быть привязан к ручному вводу заказа.

После подключения POS сценарий может стать:

```text
POS создаёт/находит заказ
      ↓
Staff bot получает OrderDraft
      ↓
идентификация клиента
      ↓
backend loyalty preview
      ↓
подтверждение / POS sync
```

ManualOrderProvider и будущие POS providers используют одинаковые application contracts.

## 23. Будущий Mini App

Staff Mini App можно добавить позже для более сложной кассовой работы. Он будет ещё одним adapter/interface над тем же backend.

Нельзя строить backend так, чтобы Telegram callback handlers являлись application services.

## 24. Подтверждённые параметры первой версии

- staff PIN: ровно 6 цифр;
- PIN задаёт admin;
- PIN уникален в организации;
- 5 ошибок PIN → блокировка на 5 минут, далее возможен progressive backoff;
- customer code TTL: 90 секунд;
- order categories настраиваются из админки;
- partial refunds поддерживаются архитектурно сразу;
- cashback без points считается от реально оплаченной денежной суммы после discounts/rewards;
- redemption 30% считается от суммы после discounts/rewards и до points;
- points целые, начисление округляется вниз.
