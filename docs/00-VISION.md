# Loyalty System V2 — видение

## Цель

Создать систему лояльности для кафе, которую можно безопасно расширять без переписывания существующих ботов, API и бизнес-логики.

Главный принцип: **backend — единственный источник истины**. Telegram-бот клиента, Telegram-бот сотрудника, web-админка и будущие интеграции являются только интерфейсами к backend.

## Что исправляем относительно V1

V1 смешивает интерфейс и бизнес-логику: отдельные решения принимаются ботами, backend доверяет переданным значениям, часть функций существует только как UI или TODO, права доступа применяются непоследовательно, а некоторые сущности используют Telegram ID вместо внутренних идентификаторов.

V2 должна исключить эти проблемы архитектурно, а не отдельными проверками.

## Архитектура верхнего уровня

```text
Client Telegram Bot ─┐
Staff Telegram Bot  ─┼──> Backend API ──> Application Services ──> PostgreSQL
Web Admin Panel     ─┤          │
Future POS / iiko   ─┘          ├──> Notifications
                                ├──> Audit Log
                                └──> Integration adapters
```

## Обязательные принципы

1. Бизнес-правила находятся только в backend.
2. Один заказ проводится одной транзакцией.
3. Баланс нельзя менять прямой записью без ledger/журнала операции.
4. Внешние идентификаторы (Telegram, POS и т.п.) не являются primary key бизнес-сущностей.
5. Все административные и денежно-подобные операции аудируются.
6. Права проверяет backend, а не интерфейс.
7. Модули общаются через стабильные сервисные интерфейсы.
8. Новые каналы (приложение, сайт, iiko) подключаются без переноса бизнес-логики.
9. Настраиваемые правила не должны требовать изменения кода там, где достаточно конфигурации.
10. API версионируется.

## Что считаем успехом

- новый тип награды добавляется без правки логики заказов;
- новый уровень лояльности добавляется настройкой/данными, а не `if` по всему проекту;
- можно заменить Telegram-бота, не затрагивая начисления и заказы;
- можно подключить POS/iiko как ещё один клиент API;
- каждая операция с баллами объяснима по журналу;
- повторный запрос не создаёт двойное списание/начисление;
- критические сценарии покрыты автоматическими тестами.
