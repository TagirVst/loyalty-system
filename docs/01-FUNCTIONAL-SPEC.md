# Функциональная спецификация V2

> Документ описывает целевую систему лояльности как самостоятельный модуль, который в будущем должен без переписывания войти в более крупную платформу управления кафе. Бизнес-правила должны быть настройками backend, а не логикой Telegram-ботов.

## 1. Клиенты

Клиент имеет внутренний ID. Основной и обязательный способ идентификации клиента — Telegram.

При регистрации используются:
- Telegram ID — определяется ботом автоматически и не вводится пользователем;
- имя;
- телефон;
- дата рождения.

Фамилия не требуется.

Функции клиента:
- регистрация и профиль;
- просмотр текущего уровня;
- баланс баллов;
- доступные награды/подарки;
- история покупок и операций лояльности;
- отзывы и предложения;
- уведомления.

Telegram является пользовательским каналом V2, но доменная логика не должна зависеть от Telegram API. Внешние POS/ERP ID в будущем хранятся как интеграционные mapping, а не заменяют Telegram-идентификацию клиента.

## 2. Сотрудники и роли

Сотрудник — отдельная сущность от клиента.

Роли V2:
- `barista`;
- `admin`.

Клиент не является сотрудником и не обязан иметь запись в RBAC сотрудников.

Права внутри backend должны быть granular permissions, даже если в первой версии ролей только две. Это позволит позже добавить manager/owner и другие роли без переписывания бизнес-логики.

### Работа общего Telegram-бота бариста

В кафе может использоваться один общий телефон и один Telegram-профиль для staff-бота.

Администратор заранее разрешает конкретный Telegram-профиль/чат как рабочее устройство. Перед началом работы сотрудник вводит персональный короткий PIN-код длиной 4–6 цифр. Backend определяет, какой Staff сейчас работает через общий Telegram-профиль.

Требования:
- PIN принадлежит конкретному активному сотруднику;
- PIN хранится только в безопасном hash-виде;
- должна существовать staff-session с временем входа и выхода/истечения;
- все операции связываются с конкретным Staff, а не только с Telegram-профилем общего телефона;
- администратор может сбросить PIN, завершить активную сессию и отключить сотрудника;
- нельзя передавать PIN как staff_id в бизнес-операции.

## 3. Идентификация клиента на кассе

Первая версия использует короткий пятизначный одноразовый код.

Код:
- генерируется backend;
- имеет TTL;
- одноразовый;
- связан с клиентом через отдельную identification session;
- после успешного использования повторно неприменим.

Код не должен быть самим `customer_id` и не должен раскрывать внутренние идентификаторы.

Архитектура должна позволять позже добавить динамический QR и другие способы идентификации без изменения заказа и loyalty-core. QR в первой версии не обязателен.

## 4. Заказ

До появления кассовой интеграции бариста вручную вводит сумму заказа и количество поддерживаемых категорий. Backend самостоятельно рассчитывает все последствия для лояльности.

На первом этапе достаточно:
- общей суммы заказа;
- количества напитков;
- количества сэндвичей;
- возможности позже добавлять другие категории без полной переделки модели.

Жизненный цикл:
1. клиент показывает пятизначный код;
2. backend определяет клиента;
3. бариста вводит сумму и категории;
4. backend рассчитывает доступное списание и возможное начисление;
5. staff-бот показывает только сведения, необходимые для текущей продажи;
6. бариста подтверждает;
7. backend одной транзакцией фиксирует заказ и все связанные операции.

Нужна идемпотентность: повтор одного и того же подтверждения не создаёт второй заказ.

## 5. Баллы

Курс V2: **1 балл = 1 рубль**.

Баллы ведутся через immutable ledger — неизменяемый журнал операций. Баланс является результатом ledger; прямое молчаливое присваивание нового баланса запрещено.

Типы операций минимум:
- начисление cashback за покупку;
- списание на покупку;
- ручная корректировка;
- бонус/акция;
- отмена/компенсирующая операция;
- сгорание, если механизм будет включён.

### Начисление

Cashback начисляется процентом от суммы покупки. Процент зависит от уровня клиента.

Если клиент использовал баллы в заказе, **новые баллы за этот заказ не начисляются вообще**, даже если баллами была оплачена только часть заказа.

### Списание

Стандартный максимальный размер оплаты баллами — **30% стоимости заказа**.

Для конкретного клиента администратор может временно установить индивидуальный лимит вплоть до 100%. Индивидуальный override обязательно имеет срок действия, после которого автоматически возвращается стандартное правило.

### Сгорание

В первой версии баллы бессрочные. Архитектура и ledger должны поддерживать будущую возможность включить срок действия и автоматическое сгорание без переделки основной модели.

## 6. Уровни лояльности

Уровни хранятся как данные и полностью настраиваются из админки.

Для каждого уровня задаются минимум:
- название;
- порядок;
- минимальная накопленная сумма покупок;
- процент cashback;
- статус активности.

Автоматический уровень определяется по общей квалификационной сумме покупок клиента.

Администратор также может назначить уровень вручную:
- бессрочно;
- до указанной даты.

Ручной уровень должен иметь приоритет над автоматическим до окончания override. После окончания backend снова рассчитывает уровень по обычным правилам.

### Понижение за неактивность

Если клиент не совершает покупок 12 месяцев, его уровень понижается на одну ступень. Если неактивность продолжается ещё 12 месяцев — ещё на одну и так далее до минимального уровня.

Период неактивности должен быть конфигурируемым, чтобы позже его можно было изменить без изменения кода.

История всех автоматических и ручных изменений уровня сохраняется.

## 7. Награды и подарки

Награда — универсальная сущность, а не отдельные поля под напиток/сэндвич.

Поддерживаемые/расширяемые типы:
- бесплатный напиток;
- бесплатный сэндвич;
- другой товар/категория;
- фиксированное количество баллов;
- фиксированная скидка;
- процентная скидка;
- произвольный будущий тип награды через зарегистрированный handler/policy.

У экземпляра награды есть источник, дата выдачи, срок действия, статус и факт использования.

Бариста не создаёт произвольный подарок. Он может только применить уже существующую доступную награду клиента в рамках правил backend.

## 8. День рождения

Birthday campaign — отдельное правило/кампания:
- включается/выключается;
- задаётся награда;
- задаётся окно автоматической выдачи;
- задаётся срок действия;
- одна и та же ежегодная награда не может быть выдана повторно за тот же период.

Механизм должен работать через планировщик и не зависеть от того, совершил ли клиент заказ в день рождения.

## 9. Акции и кампании

Нужен универсальный конструктор кампаний, основанный на заранее поддерживаемых типах условий и действий, а не на произвольном коде из БД.

Архитектура должна поддерживать минимум:
- x2/xN cashback;
- дополнительный cashback;
- подарок после заданной суммы/числа покупок;
- купи X — получи Y после появления нужных данных о товарах;
- расписание по датам, дням недели и времени;
- аудиторию по уровню/сегменту;
- лимиты применения;
- приоритет и совместимость нескольких кампаний.

Новая акция не должна требовать изменения order routes или Telegram-ботов.

## 10. Возвраты и отмена ошибочной операции

При возврате заказа backend автоматически:
- возвращает списанные при покупке баллы;
- отменяет начисленные за этот заказ баллы компенсирующей ledger-операцией;
- восстанавливает применённую награду, если это допустимо по её правилам;
- фиксирует полный audit trail.

Финансово значимые записи не удаляются.

Бариста может отменить **только свою операцию** в течение 10 минут после её проведения. Backend обязан проверить автора, срок и текущее состояние операции. После этого или для иных корректировок требуется администратор.

## 11. Ручные административные изменения

Администратор может:
- вручную начислить/списать баллы;
- назначить уровень бессрочно или до даты;
- установить временный индивидуальный лимит списания до 100%;
- выдать клиенту награду;
- отменить/скорректировать операцию в рамках разрешённых сценариев.

Для ручного изменения баллов причина обязательна. Административные изменения никогда не перезаписывают историю — они создают новые записи ledger/audit.

## 12. Отзывы и обращения

- оценка;
- текстовый отзыв;
- идея/предложение;
- обращение руководству;
- статус обработки;
- ответ/комментарий сотрудника;
- история обработки.

Точная UX-механика отзывов будет уточнена отдельно.

## 13. Уведомления

Backend создаёт задания на уведомления, канал доставки выполняет их.

Поддержать:
- персональные;
- массовые;
- системные события;
- шаблоны;
- статусы queued/sent/failed;
- повторные попытки;
- согласия/предпочтения клиента.

Telegram — первый канал, но не часть доменной логики уведомлений.

## 14. Админка

Минимум:
- dashboard;
- клиенты и карточка клиента;
- сотрудники, их PIN и активные staff sessions;
- роли/permissions;
- заказы;
- ledger баллов;
- ручные корректировки с обязательной причиной;
- уровни и их правила;
- временные overrides клиента;
- награды;
- кампании;
- отзывы/обращения;
- уведомления;
- аудит;
- настройки;
- аналитика.

Админка работает только через backend API и не обращается напрямую к БД.

## 15. Аналитика

Минимальные показатели:
- клиенты: новые/активные;
- заказы и оборот;
- средний чек;
- начислено/списано баллов;
- непогашенный балльный баланс;
- применение наград;
- распределение по уровням;
- повторные визиты;
- активность кампаний;
- отзывы.

Точный состав dashboard будет уточнён отдельно.

## 16. Интеграции и будущее в составе Cafe Management Platform

V2 запускается как самостоятельная система лояльности, но проектируется так, чтобы loyalty стал модулем большой системы управления кафе.

Интеграции изолируются адаптерами. Core не должен импортировать модели конкретной POS/ERP.

Должна существовать возможность подключить любую внешнюю систему через один из стандартных механизмов:
- provider/adapter;
- REST API;
- webhooks;
- mapping внешних идентификаторов;
- при необходимости очередь событий.

В будущем общие сущности `Customer`, `Staff`, `Location` и `Order` могут стать платформенными модулями, а loyalty будет реагировать на их события и хранить только данные своей предметной области.
