# Telegram UX V2

Документ описывает пользовательские сценарии Telegram-интерфейсов V2. Цель — современный, быстрый и минималистичный UX без необходимости запоминать команды. Telegram является первым интерфейсом, но бизнес-логика находится только в backend.

## 1. Общие принципы

- Основная навигация — inline-кнопки и редактирование текущего сообщения вместо постоянной отправки новых сообщений.
- Reply-клавиатуры использовать только там, где это действительно упрощает ввод, например запрос контакта.
- Команды `/start`, `/help` и при необходимости `/menu` остаются как базовый fallback, но пользователь не должен зависеть от команд.
- На каждом многошаговом сценарии есть `Назад` и `Отмена`.
- Все критичные действия подтверждаются отдельным preview-экраном.
- Повторное нажатие кнопки не должно создавать повторную операцию: backend обеспечивает идемпотентность.
- Callback payload содержит только безопасный короткий action/token, а не бизнес-состояние или внутренние ID.
- Состояние сценария хранится/восстанавливается через backend, чтобы перезапуск бота не ломал регистрацию или продажу.
- Ошибки показываются понятным языком и всегда предлагают следующий доступный шаг.
- Telegram deep links должны поддерживаться для акций, наград, регистрации и других контекстных переходов.
- Mini App не обязателен в первой версии, но интерфейсный контракт должен позволять добавить его без изменения core.

## 2. Архитектура Telegram-интерфейсов

```text
Backend API
  ├── Client Telegram Bot
  ├── Staff Telegram Bot
  ├── Telegram Mini App  (later)
  ├── Web Admin           (later/parallel)
  └── Future Web/Mobile
```

Telegram-боты являются thin clients. Они не считают cashback, уровни, лимиты списания, награды, возвраты или кампании.

## 3. Клиентский бот — старт

### Новый клиент

`/start`:

```text
Добро пожаловать в программу лояльности.

Регистрация займёт меньше минуты.

[ Начать регистрацию ]
```

До завершения регистрации клиент не получает рабочий loyalty account.

### Уже зарегистрированный клиент

`/start` сразу открывает главный экран, без повторной регистрации.

## 4. Регистрация клиента

Обязательные данные:
- Telegram ID — автоматически;
- имя;
- телефон — только через Telegram `Поделиться контактом`;
- дата рождения.

### Шаг 1. Имя

```text
Как вас зовут?

[ Отмена ]
```

Свободный текст с серверной валидацией длины и допустимых символов.

### Шаг 2. Телефон

```text
Поделитесь номером телефона через кнопку ниже.

[ Поделиться номером ]
[ Назад ]
```

Ручной ввод номера в основном сценарии не используется.

### Шаг 3. Дата рождения

Удобный пошаговый выбор даты/валидация. Нельзя полагаться только на произвольный свободный текст.

Перед сохранением показывается подтверждение:

```text
Проверьте данные:

Имя: Али
Телефон: +7 ...
Дата рождения: 14 мая 1994

[ Всё верно ]
[ Изменить ]
```

## 5. Главный экран клиента

Главная задача — получить код на кассе максимум за одно нажатие после открытия бота.

Пример:

```text
Тейкитерия

Gold
1 240 баллов

[ Получить код ]

[ Мои подарки ]  [ Мой уровень ]
[ История ]       [ Акции ]
[ Профиль ]       [ Оставить отзыв ]
```

Кнопка `Получить код` визуально и функционально является главным CTA.

Главный экран лучше редактировать в одном сообщении, а не создавать новый экран отдельным сообщением при каждом переходе.

## 6. Код клиента для кассы

При нажатии `Получить код` backend создаёт новую IdentificationSession.

Показывается:

```text
Ваш код

4 8 2 1 7

Покажите его бариста.
Код действует ограниченное время.

[ Обновить код ]
[ На главную ]
```

Правила:
- пятизначный;
- короткий TTL;
- одноразовый;
- не содержит customer_id;
- повторное создание может инвалидировать предыдущий активный код, если выбран режим «один активный код на клиента»;
- после успешного использования экран должен корректно отражать, что код использован/истёк при следующем обращении.

## 7. Баллы и уровень

Главный экран уже показывает текущий balance и tier.

### Мой уровень

```text
Ваш уровень: Gold
Cashback: 7%

До следующего уровня: 6 400 ₽

[ Подробнее об уровнях ]
[ Назад ]
```

Если действует ручной tier override, пользовательский текст не обязан раскрывать внутреннюю механику override, но должен показывать фактически действующий уровень и срок, если это уместно.

### Подробнее об уровнях

Показываются актуальные уровни, пороги и cashback из backend-конфигурации. Никаких hardcoded значений в боте.

## 8. Мои подарки

Сначала показываются только доступные награды.

```text
Ваши подарки: 3

☕ Напиток — 2 шт.
Действует до 20 сентября

🥪 Сэндвич — 1 шт.
Без срока

[ История подарков ]
[ Назад ]
```

При выборе награды:
- описание;
- количество;
- срок;
- условия применения;
- источник, если это полезно пользователю.

Клиент не «активирует» награду заранее, если этого не требует конкретный reward type. Использование фиксируется на продаже.

## 9. Акции

Экран показывает только актуальные кампании, подходящие клиенту.

```text
Актуальные акции

x2 cashback по пятницам
до 30 сентября

[ Подробнее ]
[ Назад ]
```

Deep link должен уметь открывать конкретную акцию напрямую из рассылки/QR/рекламы.

## 10. История

История разделяется логически, но не обязана превращаться в сложное меню.

Минимум:
- покупки;
- начисления/списания баллов;
- подарки.

Пример краткой ленты:

```text
Сегодня
Покупка 1 000 ₽
-200 баллов
Cashback не начислен

7 сентября
Покупка 850 ₽
+59 баллов
```

Пагинация — inline-кнопками с редактированием сообщения.

## 11. Профиль

```text
Профиль

Имя: Али
Телефон: +7 ...
Дата рождения: 14 мая 1994

[ Изменить имя ]
[ Изменить телефон ]
[ Изменить дату рождения ]
[ Назад ]
```

### Изменение телефона

Пользователь может сам изменить телефон только через Telegram `Поделиться контактом`.

Перед сохранением:

```text
Новый номер: +7 ...

[ Подтвердить ]
[ Отмена ]
```

Изменение фиксируется в audit/history.

### Изменение даты рождения

Клиент может самостоятельно изменить дату рождения только один раз.

До изменения явно предупреждаем:

```text
Дату рождения можно изменить самостоятельно только один раз.

Если подарок ко дню рождения уже был получен или использован в этом календарном году, изменение даты рождения не выдаст новый подарок повторно.

[ Продолжить ]
[ Отмена ]
```

Backend хранит независимый annual birthday reward claim marker / campaign issuance history. Повторная выдача определяется не текущим значением birth_date, а фактом выдачи соответствующей ежегодной награды клиенту за конкретный год/period key.

Администратор может исправить дату рождения отдельно в административном сценарии с audit trail.

## 12. Отзывы

Рекомендуемая шкала: 1–5 звёзд.

Поток:

```text
Как вам последний визит?

[ ⭐ ] [ ⭐⭐ ] [ ⭐⭐⭐ ] [ ⭐⭐⭐⭐ ] [ ⭐⭐⭐⭐⭐ ]
```

После выбора можно предложить комментарий:

```text
Хотите что-нибудь добавить?

[ Написать комментарий ]
[ Пропустить ]
```

### Положительный отзыв

Для высокой оценки можно предложить внешний отзыв:

```text
Спасибо за оценку.
Если хотите, можно также оставить отзыв о нас здесь:

[ Оставить отзыв ]
[ Не сейчас ]
```

Ссылка/площадка должна быть настройкой, а не hardcode.

### Низкая оценка

Для низкой оценки внешняя площадка не навязывается. Создаётся внутреннее обращение/уведомление администратору с контекстом визита, если он доступен.

Порог «положительного/низкого» должен быть настраиваемым.

## 13. Рассылки и сегменты

Telegram используется как первый notification channel.

Сегменты должны формироваться backend, например:
- не были N дней;
- конкретный tier;
- день рождения скоро;
- потратили больше X;
- новый клиент;
- есть неиспользованный подарок;
- другие будущие условия.

Deep link внутри рассылки ведёт сразу к нужному действию/экрану.

## 14. Заблокированный клиент

Клиент может быть заблокирован администратором.

Баллы, уровни, история, ledger и rewards физически не удаляются.

При попытке получить код/использовать программу backend возвращает controlled status. Бот показывает нейтральное понятное сообщение без технических деталей.

## 15. Ошибки и крайние состояния

Не показывать traceback, HTTP status или внутренние ID.

Примеры состояний:
- код истёк → `Код уже истёк. Создать новый?` + кнопка;
- код уже использован → предложить новый;
- клиент заблокирован → информировать о недоступности программы;
- акция завершилась → вернуть к списку актуальных;
- reward истёк → не показывать его как доступный;
- backend временно недоступен → короткое сообщение + `Повторить`;
- старое callback-сообщение → безопасно вернуть пользователя на актуальный экран.

## 16. Работа с сообщениями

Принцип: чат не должен превращаться в журнал навигационных кликов.

Для меню, списков, профиля, истории, уровней и акций преимущественно используется `editMessageText/editMessageReplyMarkup`.

Новые сообщения отправляются для событий, которые имеют самостоятельную ценность в истории:
- подтверждение покупки;
- начисление/списание;
- новый подарок;
- важная акция/рассылка;
- системное уведомление;
- ответ на обращение.

## 17. Mini App — будущий этап

V2 может стартовать без Mini App.

Позже Mini App можно использовать для:
- визуальной карты лояльности;
- истории с фильтрами;
- подарков;
- уровней;
- профиля;
- каталога акций;
- более богатого UI.

Menu button Telegram может открывать Mini App. При этом быстрый сценарий получения кассового кода должен оставаться доступен максимально быстро и не требовать обязательного запуска WebView, если нативный bot UX быстрее.

## 18. Deep links

Нужна абстракция route/deep-link handler.

Примеры концептуальных маршрутов:
- `start=campaign_<token>`;
- `start=reward_<token>`;
- `start=register_<token>`;
- `start=feedback_<token>`.

Внешний параметр не должен быть доверенным внутренним ID. Backend валидирует token/context.

## 19. Staff bot — общие UX-принципы

Детальный staff flow проектируется отдельным документом/разделом, но базовые требования уже фиксируются:
- общий Telegram-профиль кафе как terminal;
- персональный PIN бариста;
- после входа виден текущий barista/session/location;
- главное действие — `Новая продажа`;
- минимум свободного текста;
- backend preview перед подтверждением;
- `Последняя операция` для быстрого контроля/отмены в разрешённые 10 минут;
- `Выход` завершает staff session;
- сессия также завершается в конце смены.

## 20. Критерий качества UX

Для частых действий ориентир:
- клиент получает код за 1 tap от главного экрана;
- клиент видит balance и tier без дополнительных переходов;
- бариста начинает новую продажу за 1 tap после входа;
- критические изменения никогда не происходят без серверной проверки;
- основные сценарии не требуют знания Telegram-команд;
- пользователь всегда понимает, где он находится и что произойдёт после нажатия кнопки.
