# Функциональная спецификация V2

> Документ описывает целевую систему. Конкретные коэффициенты, лимиты и механики должны быть настройками, а не зашитыми константами.

## 1. Клиенты

Клиент имеет внутренний ID и может иметь несколько внешних идентификаторов: Telegram, телефон, будущий POS ID и др.

Функции:
- регистрация и профиль;
- телефон, имя, дата рождения;
- согласия и статус активности;
- просмотр текущего уровня;
- баланс баллов;
- доступные награды/подарки;
- история покупок;
- история начислений и списаний;
- отзывы и предложения;
- уведомления.

Дубликаты клиентов должны обнаруживаться и управляемо объединяться администратором.

## 2. Сотрудники и роли

Сотрудник — отдельная сущность от клиента.

Базовые роли:
- сотрудник/бариста;
- менеджер;
- администратор системы.

Права должны быть granular permissions, например `orders.create`, `rewards.issue`, `points.adjust`, `customers.read`, `analytics.read`, а не набор `if role == admin`.

## 3. Идентификация клиента на кассе

Поддержать механизм короткого одноразового кода:
- код генерирует backend;
- имеет TTL;
- одноразовый;
- связан с клиентом;
- после использования повторно неприменим.

Архитектура должна позволять позже добавить QR, карту/номер телефона или POS-идентификатор без изменения заказа как доменной сущности.

## 4. Заказ

Backend принимает фактические данные заказа и самостоятельно рассчитывает последствия для лояльности.

Жизненный цикл:
1. идентификация клиента;
2. создание/расчёт черновика;
3. backend рассчитывает доступное списание, начисление, награды и уровень;
4. интерфейс показывает расчёт;
5. сотрудник/интеграция подтверждает;
6. backend одной транзакцией фиксирует заказ и все связанные операции.

Заказ хранит внешний номер чека, источник, сумму, позиции/категории при наличии, сотрудника/интеграцию, время и статус.

Нужна идемпотентность: повтор одного и того же подтверждения не создаёт второй заказ.

## 5. Баллы

Баллы ведутся через **ledger** — неизменяемый журнал операций.

Типы операций минимум:
- начисление за покупку;
- списание на покупку;
- ручная корректировка;
- бонус/акция;
- отмена/компенсирующая операция;
- срок действия/сгорание, если будет включено.

Баланс является результатом операций ledger. Нельзя молча присвоить клиенту новое значение баланса.

Настраиваемые правила:
- курс начисления;
- максимальный процент/сумма списания;
- минимальная сумма заказа;
- округление;
- начислять ли баллы на часть, оплаченную баллами;
- категории/товары-исключения;
- срок действия баллов.

## 6. Уровни лояльности

Уровни должны храниться как данные и редактироваться из админки.

Для уровня задаются:
- название;
- порядок;
- условие достижения;
- преимущества;
- коэффициент начисления и другие модификаторы.

Критерий уровня не должен быть жёстко привязан к количеству напитков. Архитектура должна поддерживать spend, число визитов, количество определённых товаров, баллы квалификации или комбинированные правила.

История изменения уровня сохраняется.

## 7. Награды и подарки

Награда — универсальная сущность, а не отдельные поля `gift_drinks`/`gift_sandwiches`.

Примеры:
- бесплатный напиток;
- бесплатный сэндвич;
- товар;
- фиксированная скидка;
- процентная скидка;
- произвольная будущая награда.

У экземпляра награды есть источник, дата выдачи, срок действия, статус и факт использования.

Источники: день рождения, акция, достижение, ручная выдача, компенсация.

## 8. День рождения

Birthday campaign должна быть отдельным правилом/кампанией:
- включается/выключается;
- задаётся награда;
- окно выдачи и срок действия;
- защита от повторной выдачи за один период.

Она не должна запускаться только при совершении заказа: планировщик может выдать награду автоматически.

## 9. Акции и кампании

Предусмотреть расширяемый модуль кампаний:
- период действия;
- аудитория/сегмент;
- условия;
- действие/награда;
- лимиты;
- приоритет/совместимость;
- статистика применения.

Первая версия может реализовать небольшой набор правил, но модель не должна требовать переписывать заказы для каждой новой акции.

## 10. Отзывы и обращения

- оценка;
- текстовый отзыв;
- идея/предложение;
- обращение руководству;
- статус обработки;
- ответ/комментарий сотрудника;
- история обработки.

## 11. Уведомления

Backend создаёт задания на уведомления, канал доставки выполняет их.

Поддержать:
- персональные;
- массовые;
- системные события;
- шаблоны;
- статусы queued/sent/failed;
- повторные попытки;
- предпочтения/согласия клиента.

Telegram — первый канал, но не часть доменной логики уведомлений.

## 12. Админка

Минимум:
- dashboard;
- клиенты и карточка клиента;
- сотрудники/роли/права;
- заказы;
- ledger баллов;
- ручные корректировки с обязательной причиной;
- уровни;
- награды;
- кампании;
- отзывы/обращения;
- уведомления;
- аудит;
- настройки;
- аналитика.

Админка не обращается напрямую к БД.

## 13. Аналитика

Минимальные показатели:
- клиенты: новые/активные;
- заказы и оборот;
- средний чек;
- начислено/списано баллов;
- outstanding balance;
- применение наград;
- распределение по уровням;
- повторные визиты;
- активность кампаний;
- отзывы/NPS-подобная оценка при выбранной методике.

## 14. Отмена и корректировки

Удалять финансово значимые события нельзя. Используются статусы и компенсирующие операции.

При отмене заказа backend должен корректно отменить связанные начисления/списания и сохранить полный след в аудите.

## 15. Интеграции

Интеграции изолируются адаптерами. Первая внешняя интеграция может быть iiko, но core не должен импортировать iiko SDK/модели.

Система должна иметь webhook/integration слой и безопасные API credentials для машинных клиентов.
